# A2 — the `/api/admin/*-v2` gap: measured, named, handed off (2026-10-13)

**Status: DOCUMENTED and made visible in `pytest`.** Not fixed — the routes do not exist for any
caller, so no client-side change can repair them. This is the handoff for whoever implements the
server side; `tests/admin_tools_v2_gap_test.py` is the pytest-visible form of the gap.

Two things follow, and they are the whole diagnosis:

- **The 404 is not an auth artefact.** Routes that exist answer `401` before anything else; missing ones
  answer `404 {"error": "Not found"}`. The `-v2` family is missing, not forbidden.
- **The server already has the unversioned family** —
  `/api/admin/{metrics,users,invitations,overview,templates,feature-flags,settings}` all exist. The
  client asks for the versioned names instead. (`grep -o '"/api/admin/[a-z-]*"' src/python/server.py`.)

### Client-visible impact (measured, signed in as an ordinary registered user)

Loading `admin.html` with a session (registration alone is enough — the page does not check the role
before fetching):

```
404 /api/admin/metrics-v2
404 /api/admin/system-status
404 /api/admin/users-v2?limit=50
console errors: 3 × "Failed to load resource: the server responded with a status of 404 (Not Found)"
#adminRoot renders empty, 6 tabs present
```

Signed *out* these three requests are not sent at all — the A1 signed-out guard answers them locally —
which is why the 16-route console gate is green and why this gap stayed invisible: the only state that
reaches the server is the one that 404s.

## 4. Minimal spec for the server side (the handoff)

Auth: `require_admin` for the reads below; `require_admin_with_stepup` for the destructive verbs the
same script exercises (suspend / unsuspend / reset-password / force-mfa / unpublish / flag / transfer /
feature-flag PUT / impersonate / bulk). `EINVITE_ALLOW_LOCAL_ADMIN_BOOTSTRAP=1` +
`EINVITE_ADMIN_EMAIL=admin@einvite.test` is how the spec's admin gets its role.

1. **`GET /api/admin/metrics-v2`** → `200 {"cards": [{key, label, value, …}, ×8]}` whose keys are
   exactly `users, invitations, activeSessions, storage, failedLogins, rateLimitHits, jobQueueDepth,
   dbP95`. `p95` figures come from the existing metrics plumbing (`/api/admin/metrics` already computes
   the system metrics it can reuse).
2. **`GET /api/admin/system-status`** → `200` with the service-level status the dashboard polls.
3. **`GET /api/admin/users-v2?limit=&q=&offset=&unmask=`** → `200 {"items": [{id, email, role, …}],
   …}`. Emails masked by default; `unmask=1` returns real addresses; `q=` filters; `limit=` paginates.
   (The spec asserts a 10-item page, a `q=<email>` hit and an `unmask=1&limit=100` lookup.)
4. **`GET /api/admin/invitations-v2?status=&…`** → `200 [ {id, title, status, owner…} ]`, with
   `status=flagged` supported, plus `POST …/unpublish`, `…/flag`, `…/transfer`.
5. **The rest of the family** (§5) so the remaining admin tabs stop 404ing: `audit-events` (with
   `format=csv`), `health-detail` (60s cache per the spec), `reports` (+ `PUT resolve`), `jobs/{id}`,
   `bulk-{email,suspend,export,prune}`, `impersonate/{id}` + `impersonate/stop`.

**Cheaper alternative worth considering before implementing any of it:** the unversioned endpoints
already exist and already serve the same domain objects. Repointing the four client call sites at
`/api/admin/{metrics,users,invitations}` and deleting the Part-5 script would remove the gap with a
client change and no server work — at the cost of the Part-5 spec's extra response contract (the 8
card keys, masked-by-default emails, step-up auth). That is a product decision, not a bug fix, so it is
left to the owner with both options measured above.

## 5. The change to the test

The instruction was to mark the script's first `-v2` call `@pytest.mark.xfail(strict=True, reason=…)`.
**A marker inside `tests/admin_tools_test.py` would be invisible**, and this was verified rather than
assumed:

```
$ .venv/bin/python -m pytest tests/admin_tools_test.py --collect-only -q
no tests collected in 0.35s
```

That file is a script — `def main()` plus `if __name__ == "__main__"`, booting its server through
`tests.v14_test_utils.app_server` — with **zero** `def test_` functions. pytest collects nothing from
it, so the suite has never been able to report that the routes it specifies are missing, and a marker
placed there would be decoration.

So the marker went where pytest can see it: **`tests/admin_tools_v2_gap_test.py`** (new file), which
imports the spec (its `main()` is `__main__`-guarded, so importing has no side effects), boots the same
server with the same env, repeats the spec's own first call, and is marked:

```python
@pytest.mark.xfail(strict=True, reason=XFAIL_REASON)
def test_admin_metrics_v2_route_exists() -> None:
    …  spec.register(base, "admin@einvite.test"); opener = spec.login(base, "admin@einvite.test")
    status, _, data = spec._do(opener, "GET", f"{base}/api/admin/metrics-v2")
    assert status == 200, f"GET /api/admin/metrics-v2 returned {status}: {data}"
```

`strict=True` is the point: when the route lands this **XPASSes**, which pytest turns into a failure,
prompting removal of the marker and the file.

Evidence that the xfail hides nothing:

```
$ .venv/bin/python -m pytest tests/admin_tools_v2_gap_test.py -q -rxX
1 xfailed in 3.47s                       # exit 0, reason printed in full

$ .venv/bin/python -m pytest tests/admin_tools_v2_gap_test.py -q --runxfail
FAILED tests/admin_tools_v2_gap_test.py::test_admin_metrics_v2_route_exists
1 failed in 3.16s                        # the underlying gap is real: 404, not 200
```

`tests/admin_tools_test.py` itself is **untouched** — it remains the spec, exactly as the instruction
required ("Do NOT delete the test. Do NOT mock it into a pass.").

## 7. UNVERIFIED (named)

1. **Whether the routes exist elsewhere.** Nothing in this tree implements them; whether a parallel
   branch, PR or the Part-5 author's working copy does was not checked.
2. **The admin page's behaviour with a real admin session.** The impact measurement above used an
   ordinary registered user (which is enough to reach the fetches). Whether a promoted
   super-admin session changes the rendering beyond the same three 404s was not measured; promoting
   requires a direct DB update, which the spec script does and this probe did not.
3. **The remaining admin tabs' 404s** (`audit-events`, `health-detail`, `reports`, `jobs`, `bulk-*`,
   `impersonate`) are from `curl` and from reading the client's call sites — the tabs themselves were
   not each opened in a browser.
4. **The "cheaper alternative" in §4 is an option, not a measurement.** It was not implemented or
   costed.
