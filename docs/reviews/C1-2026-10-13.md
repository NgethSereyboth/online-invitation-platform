# C1 — the pre-paint language bootstrap is refused by the CSP on every route

**Bug ID:** C1 · **Severity:** high (wrong-language first paint for Khmer visitors; a console
error on all 16 routes) · **Status:** fixed, 15 of 16 routes
**Symptom:** every page logged `Executing inline script violates the following Content
Security Policy directive 'script-src 'self'' … The action has been blocked`, and the
correction that block existed to make — `html.lang` matching the visitor's stored language
*before the first paint* — never happened.

## Root cause

Every page shipped a 239-byte inline `<script>` in `<head>`:

```html
<script>(function(){try{var e=document.documentElement,v=localStorage.getItem('einvite-lang');
if(!v){var n=navigator.language||(navigator.languages&&navigator.languages[0])||"";
v=n.toLowerCase().indexOf("km")===0?"km":"en"}e.lang=v}catch(x){}})();</script>
```

The server sends `Content-Security-Policy: … script-src 'self' …`
(`src/python/server.py` → `CSP_HEADER`) with **no nonce and no hash list**, so the browser
refuses it. The CSP is correct and must not be loosened: it is the project's own policy,
there is a report-only mirror and a `/api/csp-report` rollup behind it
(`docs/security/CSP-MONITORING.md`). The pages are the side that is wrong.

It matters because the reset keys the bilingual content off the document language:

```css
[lang="km"] .i18n-en{display:none}  [lang="en"] .i18n-km{display:none}
```

so until `html.lang` matches the visitor's choice, a Khmer visitor reads the English half of
every bilingual string. The route bundle that eventually sets it is the last script on the
page.

**Measured (before).** With `einvite-lang=km` staged and the route bundle aborted — so only
a `<head>` script can set the language — the rejected inline block leaves exactly this:

| route | `html.lang` | Khmer strings visible | English strings visible | CSP violations |
| --- | --- | --- | --- | --- |
| materials.html | `en` | 0 | 22 | 2 |
| dashboard.html | `en` | 0 | 14 | 5 |
| index.html | `en` | 0 | 10 | 2 |
| public.html | `en` | 0 | 1 | 3 |

## The fix

Two changes, no new files, no `!important`, no render-blocking request added:

1. **`src/js/core/theme.js`** — the bootstrap moves into this file, which is the existing
   pre-paint persisted-preference script and is already loaded in the `<head>` of 15 of the
   16 routes. It runs at the same point in the page's life as the inline block did, one
   statement earlier.
2. **All 16 `src/html/*.html`** — the refused inline block is deleted (256 bytes per page).
   For 15 of them this is behaviour-neutral: the same logic now runs from `core/theme.js`.
   For `public.html` it removes the console error and leaves the page's language to the end
   of the bundle, which is where it already was in practice (the inline block never ran).

Why not a dedicated `core/lang-boot.js`: `build_page_manifests.py` enforces per-route
script-count ceilings that were re-baselined to the measured maxima (`public-guest: 2`,
`event-operations: 3`, `account-admin: 4`), so no route can reference one more file without
breaching its ceiling. `public.html` (which loads `backend-mode-v14.js` +
`bundle-public-v15.js` = its ceiling of 2, and not `core/theme.js`) therefore cannot host a
new tag, and it is the one route this fix does not cover — recorded as **C1b** in
`docs/reviews/bug-inventory.md` rather than hidden here.

## Not verified / open

- **C1b** — `public.html` still has no pre-paint language correction. The page's own bundle
  sets it at the end of `<body>`, exactly as it did before this fix. Options (script-count
  ceiling permitting) are to host the bootstrap in `backend-mode-v14.js`, which all 16
  routes already load in `<head>`, or to fold the two head scripts into one; both change a
  shared file's ownership and deserve their own iteration.
- **C2 / D2 / D3** — `public.html`, `dashboard.html` (3 blocks) and `index.html` (1 block,
  ~38 KB in `<head>`) still contain other inline `<script>` blocks, each refused by the same
  directive. Those blocks are separate features and are tracked individually, not folded
  into this fix.
- The Khmer strings observed are the ones already in the markup; nothing was added or
  invented.
