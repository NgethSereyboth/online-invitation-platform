# D1 — Design Studio overflow menu painted permanently over the workspace

**Symptom (one line):** on `index.html` the studio's `•••` "More" dropdown was not a dropdown
at all — it was a 286 × 505 px panel at `z-index: 12000`, painted open on a fresh load at every
width, covering ~497 px of the workspace, with no trigger that worked and no way to close it.

Status: **Fixed** · Date: 2026-10-13 · Route: `index.html` (editor / Design Studio)

---

## 1. Root cause (named, one sentence)

In the editor's static top-bar markup the menu was a **sibling** of the element that is supposed
to anchor it (`div.canvas-header-more-menu` next to `div.canvas-header-more`, not inside it) and
it shipped **without `hidden`** — so `editor-core.js`'s scoped lookup
`const menu = $('.canvas-header-more-menu', more)` returned `null`, `organizeHeader()` returned
early on its own guard, and every later line of that function — including the one that hides the
popup (`menu.hidden = true`) and the one that syncs the trigger's `aria-expanded` — never ran.

Three layers of consequence, all measured:

| Layer | Evidence |
| --- | --- |
| The popup is a permanent fixture | Pre-fix sweep `artifacts/ui-sweep.json`: `div.canvas-header-more-menu` counted as a *permanent overlay* at **all five widths** (768/1024/1280/1440/1600), `x=994..1280` at 1280 with `h=505`, `z-index: 12000`. The sweep counts only what is visible **without clicking anything**. |
| The trigger is dead | The markup's control was `<summary>` **outside any `<details>`** — not focusable, not clickable, not wired. The click pass recorded it: `{"sel":"summary","text":"MoreMore","why":"no observable state change"}`. |
| The design that is supposed to handle all this was inert | `editor-core.js organizeHeader()` (which sections the menu into Project / Editor / Advanced tools and closes it) and the two guarded creators in `canvas-plus.js` / `editor-suite.js` — all three expect the menu **inside** `.canvas-header-more`. The two creators bail on `!header.querySelector('.canvas-header-more')` (the static wrapper exists), and `organizeHeader` bails on the scoped lookup. Net: no owner. |

Why `organizeHeader`'s own comment matters — it states the contract it depends on:

> *"A menu is closed until the user opens it. … Close it here; the trigger and click-outside
> still drive it."*

Both halves of that sentence were missing from the document.

## 4. The Escape that never fired (a second, app-wide finding)

The first verification run failed 4 of 5 Escape assertions with **zero keydown events reaching
`document`**. Instrumentation (`artifacts/probe_keyscope.mjs`, `probe_keydelivery2.mjs`,
`probe_csp_detail.mjs`) traced it:

* `src/js/editor-command-system-v23.js` owns the keyboard by design —
  `window.EInviteShortcutManager.ownsGlobalKeyboard === true` — and binds
  `{id:'ui.escape', title:'Cancel or close', bindings:{standard:['Escape'], …}, run:()=>closeTopLayer()}`
  at **`window.addEventListener('keydown', keydown, true)`**, calling
  `stopImmediatePropagation()` for every matched command.
* Therefore **no `document`-level Escape handler in the app can ever run on the editor route**;
  the app's own dismissals that rely on it (`ui/app-shell.js` rail drawer, `ux-refine.js`
  inspector) are equally unreachable — recorded in the inventory, out of scope here.
* The sanctioned way in is `closeTopLayer()`'s ladder, so the popup joined it:

```diff
--- a/src/js/editor-command-system-v23.js
+++ b/src/js/editor-command-system-v23.js
 const position=$('#workflowV6Position.open');if(position){position.classList.remove('open');return true}
```

Harness note (why the first run lied): on a first-ever visit the onboarding tour is a **modal
`<dialog>`**. A modal dialog lives in the top layer — it receives the clicks aimed at the top bar
and it consumes Escape itself (its `cancel` event) — so the tour is dismissed and that dismissal
asserted before any menu check runs.
