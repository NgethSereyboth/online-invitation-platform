# A1 — signed-out pages must not fetch session-only data

Status: **fixed and verified**. 2026-10-13, against `http://127.0.0.1:4175` (the real server, not the
static preview).

## What was wrong

Every route fired its session-only fetches on load whether or not anyone was signed in, so each page
produced one browser console error per request and one failed request in the network panel. The
project's own gate measured it:

```
before:  index.html 10 console / 8 failed   dashboard.html 9 / 1   materials.html 2 / 2   public.html 3 / 1
after :  index.html  2 console / 0 failed   dashboard.html 2 / 0   materials.html 0 / 0   public.html 0 / 0
```

(The 2 lines left on index/dashboard are a Chrome verbose DOM hint and the software-WebGL deprecation
warning, not errors.) Swept across all 16 routes the same list was **37 failing requests**
(`artifacts/probe_a1_401.mjs`):

```
401 /api/invitations/demo-wedding            → /api/invitations/{comments,approvals,review-context,studio-release}
401 /api/studio/{resources,governance,releases}?invitationId=demo-wedding
401 /api/invitations                         → /api/assets  → /api/templates
401 /api/account/{security,usage,audit,sessions,passkeys,studio}
401 /api/billing/status
404 /api/admin/{metrics-v2,system-status,users-v2}      (A2 — not implemented server-side)
404 /api/invitations/demo-wedding/{polls,edit-history,signup-sheets}
```

Three separate causes sat behind that list, and only one of them was "the page forgot to check auth".

## Cause 1 — nothing owned the session contract

There was no client-side answer to "is anyone signed in?", so ~10 modules each fired first and handled
the 401 afterwards. Fix: the shared shell (`src/js/backend-mode-v14.js`, loaded `<head>`-first on all
16 routes, so no route gains a script and no byte budget moves) now exposes
`EInviteBackend.session()` / `EInviteBackend.hasSession()` — one cached `/api/auth/me` per load. Signed
out the server answers `200 {"user":null}` (verified with curl), so the probe itself never adds a
failed request.

The shell then installs a fetch guard: a same-origin `/api/*` request that is not on the
guest-reachable allowlist is **not sent** while signed out; the caller receives the same 401 JSON body
the server would have sent, so every module's existing error path runs unchanged.

The allowlist is measured, not guessed (`artifacts/probe_api_calls.mjs` records every `/api` request a
signed-out load makes): the only paths that answer 200 signed out are `/api/health` and `/api/auth/me`.
Guest-reachable writes (RSVP, poll vote, signup claim, `/api/public/*`, `/api/guest/*`) and `/api/auth/*`
are allowlisted as well, so signing in and guest actions still work. Nothing is blocked while the
backend is offline — those pages keep their own "full server required" messaging — and a successful
sign-in/sign-out invalidates the cached probe.

## Cause 2 — a local demo id was remembered as if it were real

`demo-wedding` is the app's own "nothing selected" fallback (`app.js`, `dashboard.js`, `guests.js`,
`responses.js`, `navigation-history-v23.js`), and `local-draft` is the editor's unsaved draft. Once one
of them was written into `sovan-active-invite`, `EInviteContext.getInvitationId()` returned it forever,
so the review and studio modules asked the server about a demo invitation. Signed *in* that was eight
404s per editor load — while the editor itself was open on a real invitation (`08dfadb8…`).

Fixed at the source (`src/js/invitation-context.js`): local ids are neither remembered nor returned, and
a previously stored one is purged. After the fix the signed-in editor resolves the real invitation and
the studio panels load their real data:

```
before:  404 /api/studio/governance?invitationId=demo-wedding      404 /api/studio/resources?…   …
after :  200 /api/studio/governance   200 /api/studio/resources   200 /api/studio/releases   200 /api/studio/adoption
         200 /api/invitations/c1c0796a-f3f8-4c5e-af6f-9138d484f59d
```

The shell guard also refuses requests that name a local id (`demo-*` / `local-*`), so the class cannot
come back through a future code path; it answers the 404 the server would have sent, with a
`local-invitation-id` code.

## Cause 3 — the account page tore down its own DOM

`node tools/page-errors.mjs --all` then showed one remaining console error: `account.html:
pageerror: Cannot set properties of null (setting 'textContent')`. The account page's signed-out path
replaces `<main>`, which detached `#v13SecurityStatus` while `account-security.js`'s catch was still
writing to it. The module now skips its work when there is no session (every endpoint it calls is
session-only) and its error path checks the element still exists. The whole-page teardown on a
signed-out load is still there and is recorded as its own inventory entry rather than redesigned here.

| Build determinism | `python3 build.py all --check` | exit 0 |

The signed-in half matters because a guard that blocks too much would look identical in the signed-out
numbers: `probe_a1_signed_in.mjs` registers a throwaway account and re-runs the same loads. An A/B
against the pre-change shell was also run (the guard temporarily removed, then restored) to confirm the
guard is not what keeps the signed-in dashboard from rendering.

## Limitations

* `tests/static_integrity_test.py` had a latent bug that the C1/D2 inline-script removal exposed: its
  inline-`<script>` regex matched the literal `<script>` inside the route-bundle header comment, so
  index.html "collected" a syntax error that was never a script. The extraction is now comment-aware
  (comments are not inline scripts) and the file prints `STATIC_INTEGRITY_TEST_PASSED`.
* A2 (`/api/admin/*-v2`) stays unfixed and unfixable from the client: those routes are not
  implemented in `src/python/server.py` for any caller, admin or not.
* The allowlist is a deliberate trade: an endpoint that is session-only but *not* on it would now be
  blocked signed-out rather than 401. It is derived from measurement, and the guest write paths are
  named explicitly for that reason.
