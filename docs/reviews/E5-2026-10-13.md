# E5 — Editor capture-phase Escape ownership (2026-10-13)

**Status: FIXED.** The editor's keyboard owner no longer swallows Escape when it has nothing of its
own to close, and it now owns the one piece of editor state it was missing (an active drawing tool).
App-level Escape dismissals work again while the studio is mounted.

Measured on the working tree at 2026-10-13, server `http://127.0.0.1:4175`,
`python3 build.py all --check` exit 0. Re-runnable: `artifacts/probe_e5_escape.mjs`.

---

## 1. Diagnosis — the handler, and what it did with Escape

`src/js/editor-command-system-v23.js` is the editor's global keyboard owner
(`window.EInviteShortcutManager.ownsGlobalKeyboard === true`). It binds

```js
window.addEventListener('keydown', keydown, true);   // capture, on window
```

Capture on `window` is the **first** thing any keyboard event reaches — before every
`document` listener, capture or bubble. In its `keydown()` the consumption happens
*before* the command runs:

```js
if(command.preventDefault!==false)event.preventDefault();
if(command.stopPropagation!==false){event.stopPropagation();event.stopImmediatePropagation()}
execute(id,{event});          // the result of run() was never consulted here
```

So for `Escape` — bound to the `ui.escape` command ("Cancel or close", `closeTopLayer()`) — the key
was consumed unconditionally, even when `closeTopLayer()` found nothing to close and returned
`false`. `execute()` already returns `result !== false`, but the event had been consumed by then, and
`keydown()` never waited for it.

Handlers that were therefore **unreachable** while the studio was mounted (all of them downstream of
`window` capture):

| handler | what it owns | reachable before |
| --- | --- | --- |
| `ui-layout.js` — `document` capture keydown | the canvas toolbar's `#v54ToolbarMore` `<details>` popover. Native `<details>` does **not** close on Escape itself, so this handler *is* the owner | **no** |
| `editor-core.js` — `document` keydown | the `•••` menu (fallback path for routes without the command system) | no (the ladder covers the same menu) |
| `command-palette-v23.js` — surface keydown | cancelling shortcut capture in the palette | no (the command system's `isLocalShortcutTarget` covers `[data-capturing="true"]` explicitly) |
| `accessibility-polish.js` — `document` keydown | dialog focus/inert bookkeeping | no (the ladder closes `dialog[open]` itself) |
| inline text editing on a canvas text object (`canvas-plus.js`) | committing/cancelling the edit | **yes**, via the typing guard below |

`closeTopLayer()`'s ladder, enumerated: active transform → topmost `dialog[open]` → command palette →
page-experience menu → workflow page popover → context menu → `#workflowV6Flow`/`#workflowV6Position`
→ the `•••` header menu → `inspector-open` → selection. **An active drawing tool was not in it**, and
neither was any "editor is mid-gesture" state beyond the transform.

Two guards in `keydown()` already existed and are correct: `isTypingTarget(event.target)` (so Escape
inside a field belongs to the field) and `isLocalShortcutTarget` (so surfaces that own their own keys
opt out).

## 3. Fix (one file: `src/js/editor-command-system-v23.js`)

**a. The ladder now runs before the event is consumed, and only consumes when it closed something.**
A new opt-in flag on the command, honoured in `keydown()`:

```js
{id:'ui.escape', …, repeatable:true, consumeOnlyWhenHandled:true, run:()=>closeTopLayer()}
```

```js
if(command.consumeOnlyWhenHandled){
  let handled=false;try{handled=command.run(context(event))!==false}catch(error){console.error('[V23 command]',id,error)}
  notify('executed',{commandId:id,result:handled});
  if(!handled)return;                    // nothing of ours was open: leave Escape to its owner
  if(command.preventDefault!==false)event.preventDefault();
  if(command.stopPropagation!==false){event.stopPropagation();event.stopImmediatePropagation()}
  return;
}
```

This is the mission's pattern applied at the place where the consumption actually happens: the handler
owns Escape only when it has a legitimate target to cancel. Every other command keeps the previous
behaviour (the flag is opt-in, and `ui.escape` is the only registration using it).

**b. The ladder gained the state it was missing** — an active drawing tool, ranked above the inspector
and the selection because a mode is the most transient thing on screen:

```js
const drawTool=window.EInviteToolController?.activeTool;
if(drawTool&&drawTool!=='select'&&drawTool!=='hand'){activateTool('select');return true}
```

`ui-layout.js`'s own document-capture closer for `#v54ToolbarMore` needed **no change**: it was already
correct, and it is reachable again now that the ladder falls through.

## 7. UNVERIFIED (named)

1. **The command palette's Escape path is a named skip, not a pass.** Both the `Mod+K` chord and the
   registry's own `openUI('commands')` leave `.v23-command-surface` `hidden` with zero client rects
   while `EInviteCommandUI.openState` reports `true` in this harness, so the surface could not be put
   on screen to press Escape at. The ladder's palette branch is unchanged by this fix and remains
   covered only by reading, not by measurement.
2. **A separate observation, not fixed here:** that same `openState: true` + `hidden` surface is worth
   its own look — a palette that believes it is open while painting nothing is a defect of its own
   (possibly this harness's lazy-load timing, possibly real). It is logged, not diagnosed.
3. **Other routes are unaffected by construction, not by measurement.** The command system is only in
   the index bundle (verified with `grep -l`), so the editor route is the only one this change can
   reach; the non-editor routes were not re-measured for this item.
