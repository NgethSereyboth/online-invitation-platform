# E4 — the collapsed-pane handle covered the canvas and did nothing

**Symptom (as filed):** `button.fp-mobile-pane-handle` was counted as a permanent overlay at
768/1024 — a 34 × 42 px piece of chrome painted over the content area on a fresh load.

**Symptom (as it turned out to be):** that button was also **dead**, and the thing it was supposed to
open was a one-way trap. Three defects, one affordance.

Status: **Fixed** · Date: 2026-10-13 · Route: `index.html` (editor), widths ≤ 1180

## Root causes

**1. The handle did nothing.** It called

```js
const openPane=()=>document.body.classList.remove('mobile-pane-collapsed');
```

but `mobile-pane-collapsed` is **derived state** owned by `editor-responsive-contract-v27.js`
(`window.EInviteResponsiveLayout`): its `sync()` sets
`b.classList.toggle('mobile-pane-collapsed', !creationDrawer)` from `body[data-editor-drawer]`, and a
`MutationObserver` on `body`'s class attribute re-runs `sync()` on any class change. Removing the
class by hand was therefore reverted in the same tick. Measured before the fix: click the handle at
1024 → `collapsed:true, paneWidth:66` (unchanged).

**2. It hung over the stage.** `position:fixed; left:64px; top:74px` put it just outside the 66 px rail
column, so 32 of its 34 px sat on `.stage-wrap`. Measured at 1024: handle `x:64..98`,
`stage-wrap x:0..768`, overlap `34 × 42`.

**3. Opening the pane was one-way.** All **7** `.fp-mobile-pane-close` buttons were `display:none` at
every width — the rule that positions the button also sets `display:none` and it is the last rule in
the file, so the "show on small screens" rule above never won. With the handle hidden once the pane is
open (`body:not(.mobile-pane-collapsed) .fp-mobile-pane-handle{display:none}`), there was no way back.

## Changes

| File | Change |
| --- | --- |
| `src/css/final-polish.css` | Handle moved into the rail column: `left:64px;top:74px` → `left:16px;bottom:16px` (that column is empty below the rail buttons — last rail button bottom `y:444`, handle at `y:842..884`), and the tab-only radius `0 12px 12px 0` replaced with the `--fp-radius-sm` token. Added `@media(max-width:820px){.fp-mobile-pane-handle{display:none!important}}`: below 821 px the rail column is itself translated off-canvas, so a "handle attached to the rail" cannot exist there. Appended `@media(max-width:1180px){body.studio-experience.studio-design-mode .fp-mobile-pane-close{display:block}}` so the pane keeps a visible close control. |
| `src/js/final-polish.js` | `openPane`/`closePaneOnMobile` delegate to `window.EInviteResponsiveLayout.openCreation()/closeCreation()` when present, falling back to the class toggle only for hosts without that module. |
| `src/js/editor/ui-layout.js` | `#v54SidebarCollapse` ("Toggle sidebar") now calls a `toggleSidebar()` that, at ≤ 820 px where the rail is off-canvas and the label/icon toggle has no visible effect, drives the creation drawer through the same owner; above that it keeps its label/icon job. Previously it did nothing visible in that band (measured: click → `collapsed` unchanged). |

## Verification — `artifacts/verify_e4_handle.mjs` (exit 0, 16 checks, 0 failures)

At 768: handle not shown; **topbar sidebar toggle opens the pane** (`paneWidth 290`, on-screen) and
closes it again.
At 1024 and 1180: handle shown, inside the rail column (`handle x:16..50`, rail `0..66`), **no stage
overlap** (`null`), clicking it **really opens the pane** (`paneWidth 330`, `data-editor-drawer=creation`),
and the pane's own close button collapses it again.

Sweep after the fix (`artifacts/ui-sweep-e4.json`): `index.html` overlay count **0 at 768, 1280, 1440,
1600**. At **1024 it still reports 1**, and that is a definitional artifact, not a canvas overlap: the
probe measures intersection with `main`'s *box*, and `main` at 1024 spans 0..1024 — the rail column is
inside it. Measured against the canvas: `stage-wrap x:66..1024`, handle `x:16..50`, overlap `null`. The
heuristic was deliberately **not** relaxed to hide this; it is recorded in the inventory instead.

`python3 build.py all` → **0**; `python3 build.py all --check` → **0**. Screenshots:
`sweep/e4-pane-768.png`, `sweep/e4-pane-1024.png`, `sweep/e4-pane-1180.png`.

## UNVERIFIED

- The 821–1180 band was checked at 1024 and 1180 only; 900 and 1100 were not sampled.
- Behaviour at ≤600 px is governed by the separate `mobile-editor-v14` bottom bar (which already hides
  the handle); this pass did not re-test the mobile bar's own Tools button.
