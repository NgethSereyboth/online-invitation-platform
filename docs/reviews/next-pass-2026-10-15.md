## 4. Findings

### 4.1 D1b root cause: the popup's *containing block* was a 42px box

**Verdict: fixed. Not a browser defect.** The `@position-try --studio-more-above` rule was
correct; the property it depended on was not. Fallback options are evaluated against the popup's
**containing block**, and `.canvas-header-more` — the wrapper the menu lived inside — is
`position: relative` and exactly the size of the trigger (`42px` wide, ~`22px` tall). Neither the
base placement nor the upward placement can fit inside a `42 × 22` box, so per spec the browser
correctly reverted to the base position, which left the menu hanging off the bottom of the
viewport. `position: fixed` makes the containing block the viewport — the box the fallback rule is
actually reasoning about.

`docs/reviews/D1b-2026-10-13.md` §9.1 recorded the wrong reason:

> The upward flip is unreachable on this route and is unverified. The trigger lives in the topbar…

The trigger's position in the topbar is irrelevant. Measured with the trigger 12px off the
**bottom** edge — the one position the fallback exists for — the menu still lands below the anchor
and hangs 370px outside a 420px viewport:

```
app fixture, anchor at BOTTOM   vh= 420 anchor=[386,408] menu=[412,790] h=378 flipped_up=False overflows_viewport=True
```

So the `max-height: min(620px, calc(100dvh - …))` clamp is not "what protects that case instead":
it bounds the height and does nothing about position.

#### 4.1.1 The seven hypotheses, each eliminated by measurement

| # | Hypothesis | Verdict |
| --- | --- | --- |
| H1 | `position-anchor` initial value changed `none` → `normal` (Chrome/Edge 151) | **Not the cause.** The rule sets an explicit `position-anchor: --studio-more-trigger`, and `anchor()` resolved correctly throughout (`top` computed to 412 = trigger bottom + 4). Reproduces with the explicit form on both browsers. |
| H2 | Popover UA stylesheet (`inset: 0; margin: auto`) not reset | **Not applicable.** The menu is not a `[popover]`: `<div class="canvas-header-more-menu" hidden>` at `src/html/index.html:86`, and `popover` appears **0** times in that page. |
| H3 | Missing `flip-block` / `flip-inline` / combined list | **Not the cause.** All four forms — `flip-block`, `flip-inline`, `flip-block flip-inline`, and the custom `@position-try` — failed identically while the containing block was the 42px wrapper, and all four work once it is the viewport. |
| H4 | Renamed properties (`inset-area`, `position-try-options`) | **Not the cause.** `grep -rn "position-try-options\|inset-area" src/css src/js` excluding bundles → **0 matches**. |
| H5 | Wrong containing block | **This is the cause.** Recorded in the fixture via `getComputedStyle(menu).position`, and reduced to a single-property A/B in §4.1.2. |
| H6 | Menu genuinely taller than the space above | **Eliminated by measurement.** A 60px menu that fits comfortably above the anchor *also* failed to flip while the containing block was the wrapper. |
| H7 | Transition interference (Chromium 364634027) | **Not the cause.** The fixture declares no transition at all, and the custom fallback is not driven by a transition here. |

#### 4.1.2 Minimal reproduction and the decisive A/B

Mechanically the whole defect is one property. Same markup, same rules, only the menu's `position`
varies — taken from the **live editor page** at `http://127.0.0.1:4199/index.html`, viewport
`1280x420`, real trigger moved to 12px off the bottom edge, real menu revealed:

```
BEFORE (absolute)  pos=absolute anchor y[368,408] menu x[860,1146] y[412,768] h=356 flipped=False overflows_bottom=True  viewport=1280x420
AFTER  (fixed)     pos=fixed    anchor y[368,408] menu x[860,1146] y[8,364]   h=356 flipped=True  overflows_bottom=False viewport=1280x420
```

`menu.bottom` = `364` = `anchor.top (368) - var(--space-1) (4)` — the fallback rule, doing exactly
what it says. Horizontal placement is unchanged in both rows (`left` = `860` = `anchor.right`),
so D1b's own contract ("hang from the trigger's right edge") survives the fix.

The same A/B on the extracted fixture (no app JS, no live page) gives the same verdict, and the
minimal spec-shaped control now flips too — which is what ruled out a browser defect:

```
anchor at BOTTOM  vh= 420 anchor y[386,408] menu x[420,706] y[4,382] flipped_up=True
```

The fix reverts cleanly: set the property back to `absolute` and the fixture returns to
`menu y[412,790] flipped_up=False`.

#### 4.1.3 Why the earlier pass reported "even a minimal control fails"

The first sitting concluded the environment was suspect because a minimal spec-shaped control did
not flip either. That reading was produced by a control whose containing block was *also* a small
positioned wrapper — the same latent defect, reproduced in miniature — so it reproduced the app's
symptom rather than testing the browser. With the containing block made the viewport, the browser
flips the control immediately. The earlier "phantom FLIPPED readings" note in the fixture
docstring (a page-reuse artifact) stands and is still guarded against: every measurement uses a
**fresh page**, which is why the numbers above are stable across runs.

#### 4.1.4 Test change

`tests/d1b_popover_flip_test.py` no longer contains any `xfail`. The strict xfail that marked the
gap was replaced by three passing tests, and a new one asserts the invariant the fix depends on:

- `test_menu_is_fixed_positioned` — asserts `getComputedStyle(menu).position == "fixed"`. This is
  the guard: reverting the property reintroduces the 42px containing block and silently kills the
  fallback again.
- `test_menu_opens_downward_when_anchor_is_at_top` — unchanged; the editor route's normal case.
- `test_menu_flips_upward_when_anchor_is_near_bottom` — the D1b case, now an ordinary pass.

The fixture's own trigger is now placed at `right: 420px` rather than at the viewport edge. That is
a **fixture correction, not a product change**: at the edge, `left: anchor(right)` pushed the
286px menu past the viewport's *inline* edge, which is a second, independent overflow no block-axis
flip can cure — the browser would have been right to revert there, and the fixture was measuring
its own artifact.

**On the required "before" xfail reason string:** it cannot be quoted verbatim, and this report will
not pretend otherwise. The fixture was untracked (`?? tests/d1b_popover_flip_test.py`) and was
rewritten in place, so no copy of the old string survives in the tree, in `git`, or in the pytest
cache. What the first sitting's report recorded of it, verbatim, is §2.2: the bottom-anchor case
"is a **strict xfail** that names the unresolved gap, following the same convention
`tests/admin_tools_v2_gap_test.py` used before its routes landed." The "after" string is: **there is
none** — the marker is gone and the test passes.
