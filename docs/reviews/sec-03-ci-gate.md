**Critical note on the `-ll` threshold claim:**

CI-SECURITY.md §1 and `scripts/security-scan.sh` lines 55, 59, 62, 64, 66 all state that `bandit -ll` "reports only HIGH severity findings." This is **factually incorrect**. Per the [bandit documentation](https://bandit.readthedocs.io/en/latest/), the verbosity flags work as:

| Flag | Reports |
|---|---|
| `-l` | LOW and above |
| `-ll` | MEDIUM and above |
| `-lll` | HIGH only |

With `-ll`, bandit reports 40 MEDIUM findings (all 0 are HIGH). The script exits non-zero because of MEDIUM findings, **not** HIGH findings as the comments claim. The error message `"FAIL: bandit found HIGH severity issues"` is misleading — the actual findings are all MEDIUM.

To make `-ll` report HIGH-only as documented, the script should use `-lll` instead. This is left as a recommendation (§11) — no code fix was applied in this dispatch per the "fixes land in working tree only" rule and the Phase 6B scope (GHSA placeholder only).

**B603 — subprocess call (16 LOW → all FALSE POSITIVE)**

All 16 instances use list-form `subprocess.run([cmd, arg1, arg2, ...])` without `shell=True`. Bandit flags any `subprocess.run()` call, but the list form (no `shell=True`) does not invoke a shell interpreter — there is no shell injection vector. The arguments are hardcoded command names or config-derived values, not raw user input passed to a shell.

**B404 — import subprocess (5 LOW → all FALSE POSITIVE)**

Importing the `subprocess` module is a cautionary flag, not a vulnerability. The actual usage (B603) is safe. This is expected in code that manages external processes (backup runners, malware scanners, review checks).

**B104 — hardcoded bind (2 MEDIUM → both FALSE POSITIVE)**

| File:line | Code |
|---|---|
| `core/preflight.py:115` | `if any(item in {"*", "0.0.0.0", "::"} ...): errors.append(...)` — validation check, NOT an actual bind |

**B112 — Try, Except, Continue (3 LOW → all FALSE POSITIVE)**

Same pattern as B110 — non-critical loop error handling that skips bad iterations. No security impact.

**B105 — hardcoded password (1 LOW → FALSE POSITIVE)**

`future_platform_v52/service.py:637`: `token_hash = ""` — an empty string initialization. The value is conditionally set to `hashlib.sha256(secrets.token_urlsafe(32).encode("utf-8")).hexdigest()` on the next line for non-preview mode. Bandit matches the variable name `token_hash`, but the value is not a password — it's an empty placeholder that gets populated with a cryptographic random token.

**B107 — hardcoded password funcarg (1 LOW → FALSE POSITIVE)**

`server.py:3083`: `def bot_protection_ok(self, action, token="")` — an empty string default argument. The function immediately checks `if not token: return False`. This is a parameter that must be supplied by the caller, not a hardcoded credential.

**B607 — partial path subprocess (1 LOW → Needs-Review)**

`run_review_checks.py:58`: `subprocess.run(['taskkill', '/PID', str(pid), '/T', '/F'], ...)` — uses `taskkill` without a fully qualified path. On Windows, this relies on PATH resolution. The command arguments are not user-controlled (PID comes from a tracked process object), so the risk is LOW. Recommendation: use the full path `C:\Windows\System32\taskkill.exe` for defense-in-depth.
