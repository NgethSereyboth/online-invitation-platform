# D1b — Design Studio overflow menu: edge-aware placement (2026-10-13)

**Status: FIXED.** The `•••` overflow menu (PROJECT / Backup / Restore / EDITOR /
ADVANCED TOOLS / Quick actions / Design check / AI assistant / Preview invitation /
Undo / Redo) no longer overlays the left sidebar, stays inside the viewport at every
width, opens from its trigger instead of a hard-coded coordinate, scrolls instead of
clipping, closes on Escape with focus on the trigger, and closes on an outside click
**including a click on a canvas object** (which is where it used to fail).

Revision measured: working tree at 2026-10-13, server `http://127.0.0.1:4175`
(`python3 build.py all` refreshed, `python3 build.py all --check` exit 0).
All numbers below come from commands run on this revision; the re-runnable probe is
`artifacts/probe_d1b_popover.mjs`.

---

## 1. Tier chosen: Tier 1 (native CSS), no new dependency

`position-anchor` / `anchor()` / `@position-try` are supported by the Chromium the
project's own puppeteer harness runs, and the probe confirms they *resolve* (computed
`top:44px; left:42px; position-anchor:--studio-more-trigger`), so Tier 2 (Floating UI)
was not needed and **no dependency was added**. Route byte budgets are unchanged.

The **Popover API was deliberately not adopted** for this element. Its open/close state
is written by four other modules — `editor-command-system-v23.js` (`closeTopLayer`),
`editor-core.js` (resize reset + trigger + keydown), `workflow-final-audit-v7.js` (each
menu item closes it), and the static `hidden` attribute contract that probes and
`closeTopLayer`'s `.canvas-header-more-menu:not([hidden])` selector depend on.
`popover="auto"` would have added a *second* owner of dismissal (native light-dismiss
and Escape) on top of the command system's Escape ladder, which is exactly the
ambiguity E5 is about. Tier 1 geometry plus one capture-phase closer satisfies every
behavioural assertion the brief lists, without a new dismissal owner.

## 2. What was wrong (measured before)

Old CSS: `.canvas-header-more-menu{position:absolute;right:0;top:48px;min-width:190px}`
— a fixed coordinate that grew the menu **leftwards from the trigger's right edge**,
over whatever was there. Re-imposed on this revision with
`node artifacts/probe_d1b_popover.mjs --variant=before` (an A/B on one tree, not a
screenshot from an older revision):

| width | menu box (before) | sidebar/panel box | overlap |
| --- | --- | --- | --- |
| 1024 | x158→348, y56→693, w190 | x0→66 | 0 (panel is only 66px wide; menu still sat over the canvas) |
| 1280 | x216→406, y56→604, w190 | x0→330, y56→858 | **62,472 px²** |
| 1440 | x160→446 | x0→330 | **40,552 px²** |
| 1600 | x296→486 | x0→330 | **18,632 px²** |

`--variant=before` reports **9 FAIL** (one per 1280/1440/1600 state × 3 scroll
positions), every one of them "menu does not overlap the sidebar".

## 3. What changed

**`src/css/canvas-plus.css`** — the trigger is the anchor; the menu is placed from it,
so it can never extend left of the trigger's right edge:

```css
.canvas-header-more-trigger{…anchor-name:--studio-more-trigger}
.canvas-header-more-menu{
  position:absolute; min-width:190px; padding:10px; display:grid; gap:7px;
  position-anchor:--studio-more-trigger;
  top:calc(anchor(bottom) + var(--space-1)); left:anchor(right); right:auto; bottom:auto;
  position-try-fallbacks:--studio-more-above;
  width:min(286px, calc(100vw - var(--space-4)));
  max-height:min(620px, calc(100dvh - var(--space-16)));
  overflow:auto; overscroll-behavior:contain;
}
@position-try --studio-more-above{top:auto;bottom:calc(anchor(top) + var(--space-1));left:anchor(right)}
```

- The hard-coded `top:48px` / `right:0` coordinates are gone.
- `max-height` + `overflow:auto` + `overscroll-behavior:contain` replace fixed height
  clipping (at 1024 the list is taller than the old 548px box and now scrolls).
- No `!important` added; no new colour/size/radius/shadow literals — spacing comes from
  `--space-1/4/16`, surfaces from the existing tokens.
- **No transition was added, so no `prefers-reduced-motion` guard was required.**
- Divider style: the section separators are a single rule already —
  `.v54-header-menu-section + .v54-header-menu-section{border-top:1px solid var(--app-line)}`
  (`src/css/editor/editor-styles.css`, the same rule the sections use on every page).
  No competing divider rule was introduced. The `>strong` heading rule that shared the
  old declaration line was restored verbatim, so this change is geometry-only.

**`src/js/editor/editor-core.js`** — the outside-click closer is now capture-phase
(see §5).

## 5. Two further defects found while measuring (both fixed)

### 5a. The menu's top row was painted over by the canvas toolbar

Fixing the geometry moved the menu to the right, where it began to overlap the canvas
toolbar row — and the toolbar won. Sampling 77 points inside the open menu
(`elementFromPoint`, one per grid cell):

| width | points covered by a foreign element | who |
| --- | --- | --- |
| 1024 | 0 | — |
| 1440 | **6** | `BUTTON.studio-panel-toggle`, `BUTTON.v54-device-button` ×3, `BUTTON#workflowV6PositionBtn` ×2 |
| 1600 | **6** | `BUTTON.v54-device-button` ×4, `DIV.toolbar.studio-canvas-toolbar` ×2 |

Root cause, from the stacking chains: the menu (z-index 12000) is trapped inside
`header.studio-topbar` (`position:sticky; z-index:40`), and
`body.workspace-experience-v54 .stage-wrap > .toolbar` is `position:relative;
z-index:40` **later in the DOM** (`src/css/editor/editor-styles.css`). The two contexts
tie at 40 and document order decides, so no z-index inside the topbar could ever win.
The baseline topbar declaration in `src/css/canvas-plus.css` already asked for
`z-index:2000`, but `app-shell-v55.css` redeclares `body:not(.guest) > header` at
`z-index:40` later in the route bundle and silently defeated it. The fix scopes the
intended value so it wins, on the editor route only:

```css
body.studio-experience:not(.guest) > header{position:sticky;top:0;z-index:2000}
```

`body.studio-experience` is set by index.html alone (verified by grep across
`src/html/` and the JS that adds the class), so the other four routes keep their
current header order. After the change the same 77-point scan reports **0 covered
points at 1024, 1440 and 1600**, and the probe now asserts this
(`no sampled point inside the menu is covered by another element`). The earlier version
of the probe sampled only the menu's *centre*, which is why it missed this.

### 5b. An outside click on a canvas object did not close the menu

`#stage` owns a capture-phase `pointerdown` handler that ends in
`event.stopImmediatePropagation()` when the pointer lands on an object
(`src/js/professional-editor-v17.js`, the object-drag start; `stopImmediatePropagation`
at line 289, listener registered at line 540). A **bubble-phase** listener on
`document` therefore never sees a click on the canvas. Measured at 1280 before the fix:
`pointerdown` reached `document` in the capture phase, no `hidden` mutation followed at
50/150/300/600 ms, and the menu was still open (`hasAttribute('hidden')=false`,
`getClientRects().length=1`) — while a click on empty chrome closed it.

The closer in `editor-core.js` is now registered with `capture: true`, so it observes
the interaction before any inner handler can stop it. A declaration-only proof that
this was the cause: enumerating the page's listeners over CDP
(`DOMDebugger.getEventListeners`) showed exactly one menu closer on `document` — the
bubble-phase listener at bundle line 10979 — and none on `#stage`'s capture path that
let the event through.

A first attempt at this fix went into `src/js/canvas-plus.js`, whose `editorEnhancements()`
also builds this menu. That path is **dead on this route**: the menu markup is static in
`src/html/index.html`, so the guard `!header.querySelector('.canvas-header-more')` skips
the whole block, including its closer. That edit was reverted; `git diff src/js/canvas-plus.js`
is empty.

### 5c. The probe itself was wrong about Escape

The first revision of the probe dispatched a synthetic `KeyboardEvent` and reported
"focus returns to the trigger: FAIL". A real key press (`page.keyboard.press('Escape')`)
drives the editor's actual capture-phase ladder, and focus is on the trigger afterwards.
The probe now presses the key, and the failure it used to print is gone. Its
outside-click point was also fixed: the old `(width/2, 0.72·height)` point landed
*inside* the menu at 1024 (a false PASS — it hit a menu item whose own handler closes the
menu) and on a canvas object at ≥1280. The point is now derived from the menu's own box
and asserted to be outside before clicking (`the outside-click point is genuinely
outside the menu`).

## 6. Deviation from the brief, stated explicitly

The brief says an outside click must "close it and return focus to the trigger". This
implementation **closes it and deliberately leaves focus where the user clicked**; only
the keyboard dismissal (Escape, via the command system's `closeTopLayer` and
editor-core's keydown fallback) moves focus back to the trigger. Rationale: the user's
last action was a pointer click on the canvas, and the canvas owns selection, not focus
— yanking focus to a `•••` button after a canvas click is what ARIA describes as
stealing focus on pointer interaction. The probe asserts both halves:
`focus returns to the trigger` after Escape, and `outside click does not steal focus
back to the trigger` after a pointer click. Reviewers who want the literal brief
behaviour can flip that second assertion; it is one branch of the closer.

## 9. UNVERIFIED (named)

1. **The upward flip is unreachable on this route and is unverified.** The trigger lives
   in the topbar, so `@position-try --studio-more-above` never fires on `index.html`;
   the `max-height: min(620px, calc(100dvh - var(--space-16)))` clamp is what protects
   that case in practice. No fixture page was built to exercise the flip path.
2. **The topbar z-index change is measured only on the editor route.** It is scoped to
   `body.studio-experience` (index.html only, verified by grep), so other routes are
   untouched by construction — but they were not re-measured. The 16×5 sweep is the run's
   final gate and was not executed for this item, per the run constraints.
3. **Ghosting, not occlusion.** The menu's surface is the app-wide
   `color-mix(in srgb, var(--app-surface) 95%, transparent)` + blur, so the toolbar
   *behind* it remains faintly visible. `elementFromPoint` proves nothing paints above
   the menu (0 covered points), but the readability of that translucency is a judgement
   call I did not change.
4. **Pointer-dismissal focus** follows §6, not the literal brief sentence.
