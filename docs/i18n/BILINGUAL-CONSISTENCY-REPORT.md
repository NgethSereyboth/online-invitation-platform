## Pattern detection

The script recognises two bilingual string-table conventions:

- **Pattern A (per-key):** `STRINGS = { key1: { en: '...', km: '...' }, ... }`
  — used by `signup-sheets.js`, `polls.js`, `album.js`, `invitation-edit-history.js`, `host-signup-sheets.js`, `host-polls.js`, `toast.js`, `delivery-dialog.js`.

- **Pattern B (per-locale):** `STRINGS = { en: { key1: '...' }, km: { key1: '...' } }`
  — used by `collaboration-presence-v52.js`, `crdt-yjs-indexeddb.js`, `crdt-yjs-rich-media.js`, `crdt-yjs-undo.js`, `guest-journey.js`.

A hand-rolled brace-balanced scanner walks every `{...}` object literal in the file (skipping string contents and `//` + `/* */` comments). For each object it looks at the identifier before `:` before `{` to decide which pattern applies, then extracts the inner `en:` / `km:` string values.

## Adding a new legitimate exception

If a brand-new proper noun or acronym enters the platform (e.g. a new third-party integration), add it to `DEFAULT_EXCEPTION_STRINGS` in `scripts/check-bilingual-consistency.py`. The string must:

1. Have no Khmer translation (verify with a native speaker).
2. Be a proper noun, brand name, or technical acronym.
3. Be used in EN mode as-is (no transliteration).

For one-off overrides (e.g. an experimental string in a PR branch), use the `--allow-identical` CLI flag instead of editing the default list:

```bash
python3 scripts/check-bilingual-consistency.py --strict \
  --allow-identical 'NewBrand,new-acronym'
```

## CI integration

Add to `.github/workflows/bilingual-check.yml`:

```yaml
name: Bilingual consistency
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.x'
      - name: Check bilingual consistency
        run: python3 scripts/check-bilingual-consistency.py --strict
```
